# Roadmap: пошаговое внедрение SaaS-бота модерации

## Цель

Построить white-label SaaS для модерации Telegram-чатов с жёстким разделением на:

- `Control Plane` — настройка правил и управление тенантами
- `Event Gateway` — приём и маршрутизация входящих событий
- `Detection Pipeline` — быстрый и медленный контуры анализа
- `Policy Engine` — принятие решения и применение санкций
- `Audit & Appeals` — журнал, апелляции, дообучение

Ключевой принцип внедрения: не начинать с набора микросервисов. Для MVP и первых production-итераций идти через модульный монолит с чёткими интерфейсами, очередями и изолированными доменными пакетами. Вынос в отдельные сервисы делать только после появления реальной нагрузки, организационной границы или эксплуатационной боли.

## Архитектурные решения на старте

- Базовый стек: `Go + PostgreSQL + Redis + RabbitMQ/NATS`
- Runtime-модель: `1 API/Gateway процесс + 1..N worker-процессов`
- Хранилище конфигурации: `PostgreSQL`
- Горячий кэш правил чата: `Redis`
- Асинхронная обработка событий: очередь
- Аудит и апелляции: отдельные таблицы в `PostgreSQL`
- Векторный поиск: подключать после стабилизации Fast Path, не в первой поставке
- LLM/Vision: только после того, как Fast Path, policy и audit дают управляемый baseline

## Принципы поставки

- Каждый этап должен давать работающий end-to-end результат
- Новая функциональность включается через feature flags
- Контракты событий и данных фиксируются до реализации
- Любой этап закрывается только после тестов, метрик и обновления документации
- Все решения должны поддерживать tenant isolation и идемпотентную обработку

## Поток внедрения по фазам

### Фаза 0. Foundations и tracer bullet

Цель: собрать минимальный скелет системы, на котором можно доказать жизнеспособность архитектуры.

**Что делаем**

- [ ] Зафиксировать bounded contexts:
  - `controlplane`
  - `gateway`
  - `detection`
  - `policy`
  - `audit`
- [ ] Описать основные доменные сущности:
  - `Tenant`
  - `Chat`
  - `RuleSet`
  - `IncomingEvent`
  - `DetectionResult`
  - `PolicyDecision`
  - `ModerationAction`
  - `Appeal`
- [ ] Утвердить формат внутренних событий:
  - `message.received`
  - `user.reported`
  - `scan.requested`
  - `decision.made`
  - `action.applied`
  - `appeal.requested`
- [ ] Поднять локальную инфраструктуру: `PostgreSQL`, `Redis`, очередь, миграции, env-шаблоны
- [ ] Создать модульный каркас проекта с интерфейсами между доменами
- [ ] Настроить базовую observability:
  - структурные логи
  - correlation id
  - базовые metrics
  - health/readiness probes

**Tracer bullet**

- [ ] Реализовать один сквозной сценарий:
  - webhook получает новое текстовое сообщение
  - gateway кладёт событие в очередь
  - worker забирает событие
  - simple regex/link heuristic считает сообщение спамом или нет
  - policy принимает решение `allow` или `delete`
  - действие и причина пишутся в audit log

**Критерий завершения**

- Один чат можно подключить и прогнать по end-to-end пайплайну без ручных доработок
- Есть повторяемый локальный запуск и smoke test
- В коде уже выделены доменные границы, а не один общий пакет "bot"

### Фаза 1. Single-tenant moderation MVP

Цель: получить рабочий антиспам-контур для одного чата или малого числа чатов без полноценного SaaS-управления.

**Что делаем**

- [ ] Сделать приём событий Telegram устойчивым к ретраям и дублям
- [ ] Добавить idempotency key на входящее событие
- [ ] Реализовать минимальный RuleSet:
  - включён ли антиспам
  - список запрещённых паттернов
  - список запрещённых ссылок
  - порог эвристического риска
- [ ] Вынести нормализацию текста в отдельный модуль:
  - lower-case
  - очистка шума
  - сведение похожих символов
  - ограничение длины
- [ ] Реализовать Fast Path v1:
  - regex
  - стоп-слова
  - link/domain heuristics
  - rate-based heuristics на пользователя
- [ ] Реализовать Policy Engine v1:
  - `allow`
  - `delete`
  - `mute`
  - `ban`
- [ ] Реализовать безопасный Action Executor с повторной доставкой и idempotency
- [ ] Записывать все решения в audit log с причиной, score и источником сигнала

**Критерий завершения**

- Есть стабильная модерация текстового спама в production-like среде
- По каждому срабатыванию видно: что пришло, что сработало, какое решение принято
- Ошибка во внешнем Telegram API не ломает весь пайплайн

### Фаза 2. Control Plane MVP

Цель: убрать ручное редактирование конфигов и дать администраторам управляемый интерфейс.

**Что делаем**

- [ ] Спроектировать tenant model:
  - владелец
  - набор чатов
  - роли администраторов
  - лимиты и статус подписки
- [ ] Сделать `Telegram Mini App` как базовый UI администрирования
- [ ] Реализовать Backend API для:
  - подключения чата
  - управления правилами
  - просмотра последних срабатываний
  - управления whitelist/blacklist
- [ ] Завести `PostgreSQL` как source of truth для конфигурации
- [ ] Ввести `Redis` как runtime cache конфигов
- [ ] Реализовать инвалидацию кэша после обновления настроек
- [ ] Добавить версионирование RuleSet, чтобы worker понимал, какой конфиг применялся
- [ ] Ограничить доступ по ролям: owner/admin/viewer

**Критерий завершения**

- Админ может изменить правила без деплоя и без рестарта воркеров
- Изменение настроек начинает действовать почти сразу через cache refresh
- Конфигурация и runtime-пайплайн не связаны напрямую через shared mutable state

### Фаза 3. Multi-tenant core

Цель: превратить single-tenant решение в безопасный SaaS-контур.

**Что делаем**

- [ ] Ввести полноценную изоляцию данных по tenant id на всех уровнях
- [ ] Перенести все ключевые сущности на tenant-aware схему:
  - конфиги
  - аудиты
  - санкции
  - апелляции
  - usage counters
- [ ] Добавить квоты:
  - сообщений в минуту
  - LLM/Vision budget
  - хранение истории
- [ ] Ввести federation model:
  - локальные правила чата
  - федеративные баны
  - наследование политик
- [ ] Добавить soft-delete и безопасный offboarding tenant-а
- [ ] Реализовать rate limiting на API и административные операции

**Критерий завершения**

- Несколько независимых тенантов могут работать параллельно без утечки правил, данных и санкций
- Tenant isolation проверен тестами и аудитом запросов

### Фаза 4. Fast Path production-grade

Цель: сделать дешёвый контур основным источником сигнала и разгрузить дорогие модели.

**Что делаем**

- [ ] Усилить нормализацию:
  - кириллица/латиница
  - zero-width и спецсимволы
  - emoji noise
  - OCR-ready text extraction pipeline hooks
- [ ] Добавить детекторы:
  - flood
  - repeated payload
  - suspicious mentions
  - username/profile heuristics
  - reputation signals
- [ ] Подключить векторный индекс только после базовой стабилизации:
  - эмбеддинги для известных нарушений
  - nearest-neighbor по похожим спам-шаблонам
  - per-tenant или shared corpora с изоляцией правил применения
- [ ] Ввести единый `Risk Score`
- [ ] Добавить explainability payload:
  - какие правила сработали
  - какой вес у каждого сигнала
  - почему принято именно такое решение

**Критерий завершения**

- 80-90% типового спама режется без вызова LLM/Vision
- Fast Path даёт предсказуемый score и объяснение
- У команды есть метрики false positive / false negative по основным классам

### Фаза 5. Policy Engine v2

Цель: отделить детекцию от бизнес-решений и сделать санкции настраиваемыми.

**Что делаем**

- [ ] Вынести policy rules в отдельный модуль с чётким интерфейсом
- [ ] Поддержать разные профили строгости:
  - permissive
  - balanced
  - strict
- [ ] Сделать матрицу действий по типу риска:
  - spam
  - abuse
  - nsfw
  - scam
  - raid/flood
- [ ] Добавить escalation chain:
  - warn
  - temporary mute
  - delete + mute
  - permanent ban
- [ ] Учитывать контекст:
  - история пользователя
  - давность нарушений
  - роль в чате
  - исключения и whitelist
- [ ] Ввести dry-run режим для безопасной выкладки новых правил

**Критерий завершения**

- Одинаковые сигналы могут приводить к разным действиям в зависимости от политики тенанта
- Новые policy rules можно включать без переписывания детекторов

### Фаза 6. Slow Path: LLM и Vision

Цель: подключить дорогой интеллект только там, где он реально нужен.

**Что делаем**

- [ ] Разделить очереди на `fast` и `slow`
- [ ] Формализовать причины эскалации в Slow Path:
  - ambiguous fast result
  - image/video content
  - user report
  - high-risk tenant policy
- [ ] Добавить LLM-контур:
  - анализ контекста последних сообщений
  - классификация спорных кейсов
  - структурированный JSON-ответ
- [ ] Добавить Vision/OCR-контур:
  - извлечение текста с изображений
  - базовые модерационные категории
  - объединение с Fast Path сигналами
- [ ] Ввести budget control:
  - лимиты по тенанту
  - лимиты по типу события
  - fallback при исчерпании бюджета
- [ ] Ввести prompt/version registry, чтобы можно было воспроизводить решения

**Критерий завершения**

- Slow Path не участвует в каждом сообщении
- Все вызовы дорогих моделей измеряются, лимитируются и трассируются
- Решение воспроизводимо: видно модель, prompt version и исходный контекст

### Фаза 7. Audit, review и appeals

Цель: сделать систему операционно управляемой и пригодной для разбора ошибок.

**Что делаем**

- [ ] Построить полный audit trail:
  - исходное событие
  - результаты детекторов
  - policy decision
  - исполненное действие
  - финальный статус
- [ ] Добавить UI/API для просмотра инцидентов
- [ ] Добавить репорты пользователей и очередь ручного review
- [ ] Реализовать апелляции:
  - пользовательская заявка
  - авторазбор
  - эскалация к человеку
- [ ] Поддержать replay инцидента на тех же входных данных
- [ ] Ввести reason taxonomy для дальнейшей аналитики

**Критерий завершения**

- Любое спорное решение можно разобрать без доступа к прод-логам вручную
- У системы есть контролируемый контур обработки false positives

### Фаза 8. Feedback loop и самообучение

Цель: превратить накопленный audit в источник улучшения Fast Path и policy.

**Что делаем**

- [ ] Собрать pipeline разметки:
  - confirmed spam
  - false positive
  - missed spam
- [ ] Построить генератор кандидатов:
  - новые regex
  - новые стоп-фразы
  - новые похожие векторные шаблоны
- [ ] Ввести review-слой перед публикацией новых правил
- [ ] Версионировать knowledge base и уметь откатывать неудачные обновления
- [ ] Настроить A/B или shadow rollout новых детекторов
- [ ] Отдельно хранить tenant-local knowledge и global knowledge

**Критерий завершения**

- Новые обнаруженные паттерны попадают в Fast Path без ручной пересборки всей системы
- Есть безопасный процесс публикации и отката knowledge updates

### Фаза 9. SaaS hardening

Цель: довести продукт до состояния масштабируемого сервиса.

**Что делаем**

- [ ] Billing и usage metering
- [ ] Плановые ограничения и feature gating
- [ ] Tenant onboarding/offboarding flows
- [ ] Резервное копирование и disaster recovery
- [ ] SLO/SLA и error budget
- [ ] Горизонтальное масштабирование воркеров
- [ ] Перенос отдельных доменов в сервисы только при доказанной необходимости:
  - отдельный ingestion service
  - отдельный detection worker pool
  - отдельный appeal/review service
- [ ] Security hardening:
  - secrets management
  - audit доступа админов
  - шифрование чувствительных данных
  - retention policy

**Критерий завершения**

- Система может обслуживать множество тенантов с прогнозируемой стоимостью
- Есть эксплуатационные runbooks и понятный путь масштабирования

## Сквозные задачи, которые нельзя откладывать

### Наблюдаемость

- [ ] Метрики по очередям, latency, ошибкам Telegram API, cache hit ratio, стоимости LLM/Vision
- [ ] Алёрты по backlog, росту false positives, деградации slow path
- [ ] Dashboard по tenant usage и moderation outcomes

### Тестирование

- [ ] Unit-тесты доменных правил и policy
- [ ] Contract-тесты внутренних событий
- [ ] Integration-тесты `gateway -> queue -> worker -> action`
- [ ] Load-тесты на burst spam-атаки
- [ ] Replay-тесты на реальных anonymized кейсах

### Безопасность

- [ ] Tenant isolation tests
- [ ] Access control review
- [ ] Secret rotation
- [ ] Data retention и удаление персональных данных

### Документация

- [ ] ADR на ключевые решения
- [ ] Схемы событий и sequence diagrams
- [ ] Runbooks на инциденты
- [ ] Описание operational limits и rollback-процедур

## Приоритет поставки

Если идти максимально прагматично, порядок релизов должен быть таким:

1. `Фаза 0` — скелет и tracer bullet
2. `Фаза 1` — рабочий single-tenant антиспам
3. `Фаза 2` — управление конфигами через TMA/API
4. `Фаза 3` — multi-tenant core
5. `Фаза 4` — production-grade Fast Path
6. `Фаза 5` — зрелый Policy Engine
7. `Фаза 6` — Slow Path с LLM/Vision
8. `Фаза 7` — audit, appeals, review
9. `Фаза 8` — feedback loop
10. `Фаза 9` — SaaS hardening и масштабирование

## Что сознательно не делаем в первой поставке

- Не строим сразу набор независимых микросервисов
- Не подключаем LLM/Vision до появления реальной потребности
- Не делаем auto-learning без audit trail и human review
- Не смешиваем конфигурационный API, detection-логику и action execution в один бесконтрольный модуль
- Не принимаем решения на основе "магии модели" без explainability и replay

## Определение готовности MVP

MVP можно считать состоявшимся, когда выполнены все условия:

- Один tenant может подключить чат и управлять правилами без вмешательства разработчика
- Fast Path блокирует основную массу очевидного спама
- Policy Engine применяет хотя бы `allow/delete/mute/ban`
- Все решения попадают в audit log
- Есть базовая админка или TMA для просмотра правил и последних инцидентов
- Система выдерживает burst-нагрузку без потери входящих событий

## Следующий практический шаг

Если переходить к реализации прямо сейчас, стартовый execution order должен быть таким:

1. Утвердить контракты событий и доменные сущности
2. Поднять локальную infra-среду и миграции
3. Реализовать tracer bullet `webhook -> queue -> fast heuristic -> policy -> audit`
4. После этого разворачивать control plane и tenant model
